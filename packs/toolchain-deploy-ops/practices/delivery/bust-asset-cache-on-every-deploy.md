## When to apply

Apply on every release of a static site or front-end bundle whose assets are served with long cache
lifetimes. Also apply when triaging "the site is white/broken for some users but fine for me" reports
that start right after a deploy - the first suspect is a mixed old/new generation, not a code bug.

## Guidance

Make the entry document the single version carrier. Keep exactly one version token in the entry HTML,
bump it in the same commit as the content change, and package the deploy from that commit so the live
token can be compared against the repository token. Serve the entry document with a no-cache policy
while asset URLs stay long-cached, so returning browsers always re-read the token and request the new
asset generation.

When a sub-application cannot carry a query-string token because its internal URLs are generated by
its own runtime, publish each build into a versioned directory and atomically flip a symlink that the
entry URL points at; the flip is the cache bust. Give the entry points of that sub-application their
own no-cache rules at the same time.

After deploying, fetch the live entry document and confirm the token equals the intended one; a token
that did not change is a failed release even if the upload succeeded.

## Why

Cache duration is a promise that a URL's content is immutable for that window. Without a token in the
URL, every asset path keeps its identity across releases, so a browser can legally combine a cached
old bundle with a freshly fetched entry, or vice versa. Because the entry document is the one file
that is always revalidated, it is the only reliable place to put the generation marker. The failure
mode is asymmetric and easy to misread: developers who hard-refresh never see it, while the affected
users get a mixed build whose symptom (a framework that never mounts, a global that is undefined)
looks nothing like a caching problem.

## Exceptions and boundaries

Content-hashed filenames generated by a build pipeline need no manual token: the URL changes with the
content, so the bust is automatic. Do not "fix" the problem by disabling caching globally - that
trades a correct generation boundary for permanent bandwidth cost and hides the missing discipline.
Do not depend on users to hard-refresh, and do not treat a successful upload as a successful release:
the live token check is the release gate.

## Example

A release ships a new application bundle that reads a template global which only the new entry
document loads. A returning browser keeps the cached old entry document, so the global is never
defined; the framework mounts nothing and the page is blank while the assets are all present on the
server. The fix is two-part: bump the version token before packaging, and keep a no-cache policy on
the entry document so the next release cannot mix generations. Verifying the live entry's token became
part of the deploy checklist.
